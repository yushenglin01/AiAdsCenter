# ADR-0005：事务 Outbox 与 Asynq 异步执行

* 状态：Accepted
* 日期：2026-08-04
* 决策迭代：DEV-20260804-006

## 背景

经营分析包含上下文读取、模型调用、校验与多表持久化，HTTP 同步执行会放大超时和重试风险。仅在数据库提交后直接写 Redis，又存在“数据库成功、队列失败”的双写缺口。

## 决策

在创建 `agent_tasks` 的同一 MySQL 事务内写入 `task_outbox`。API 做一次即时投递，Worker 内置 dispatcher 周期扫描补偿；Asynq 负责任务持久化、超时、有限重试和优雅停机。业务 task UUID 同时作为 Asynq TaskID，重复投递视为幂等成功。Worker 的业务状态仍以 MySQL 为权威，使用条件更新、心跳租约和终态短路防止重复副作用。

## 结果

API 可以稳定返回 202，不依赖 Worker 当时在线；Redis 暂时不可投递时任务仍留在 Outbox。代价是形成 MySQL 与 Redis 两套状态，需要 dispatcher、租约恢复、运维监控和清理策略。Asynq v0.26.0 的公共 API 仍是 v0，升级前必须重新运行队列契约测试。

## 未选择方案

* HTTP 内同步执行：无法满足可恢复异步工作流。
* 数据库提交后直接投递：存在不可恢复双写窗口。
* 立即拆分独立工作流微服务：超出当前模块化单体 MVP 的复杂度边界。
